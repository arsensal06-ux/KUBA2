# KubanAdventures — доработанный проект

Статический сайт на HTML/CSS/JS с Firebase Auth и Firestore. Сборка не нужна.

## Что изменено

- Общие исходные данные туров для сайта и админки; сохранены 8 маршрутов из исходного проекта.
- 11 локальных WebP-изображений: главный фон, семь регионов, внедорожник, квадроцикл и SUP. Это AI-иллюстрации, а не документальные снимки маршрутов. Внешние ссылки для них не нужны.
- Обложки карточек, безопасное поле изображения и предпросмотр в админке. Допустимы прямые HTTPS-ссылки и файлы `images/...`.
- Палитра публичного сайта согласована с зелёно-медной админкой; адаптация под телефон.
- Firestore `onSnapshot`: туры, заголовок, статистика, описание, телефон, email и адрес обновляются у посетителей без перезагрузки после успешного сохранения в админке.
- Активный фильтр не сбрасывается при обновлении данных. Пустой массив туров с сервера корректно удаляет все карточки.
- Кэш отображается при запуске/потере сети, но никогда не перекрывает данные сервера устаревшей локальной копией.
- Полное описание маршрута, включённые услуги и экипировка теперь доступны посетителям.
- Форма заявки вместо `prompt`; заявки и их статусы синхронизируются с админкой и личным кабинетом через Firestore.
- Удалена фиктивная авторизация с любым паролем. Production-доступ — через Firebase Auth, права записи — через серверные Firestore rules.
- Ошибка базы не выдаётся за успешную публикацию/отправку. Черновик формы остаётся доступен для повторной попытки.
- Пароли не хранятся в localStorage. Firebase SDK и иконки включены локально. Добавлен сброс пароля.

## ВАЖНО: что не выполнено автоматически

Архив содержит готовый код, но он не загружен на ваш хостинг. У меня нет административного доступа к вашему Firebase, поэтому **правила базы, email-подтверждение, домены Auth и реальная межустройственная синхронизация в вашем проекте ещё требуют проверки владельцем**. Тесты приложения используют подменённый Firebase, не ваш production-проект. Не публикуйте сайт с открытыми правилами `allow write: if true`.

### Настройка Firebase владельцем

1. Откройте Firebase Console → проект `kubanadventures` (или создайте свой и замените web-конфигурацию в `assets/js/config.js`). Web API key — публичный идентификатор, он не заменяет правила доступа. Сервисный ключ в этот проект добавлять нельзя.
2. Authentication → Sign-in method → включите **Email/Password**. Создайте аккаунт владельца с вашим адресом. Убедитесь, что этот аккаунт под вашим контролем.
3. Для текущего проекта адрес администратора — адрес из исходного архива, `arsensal06@gmail.com`. Если меняете владельца, измените адрес **и** в `config.js`, **и** в `firestore.rules`.
4. Подтвердите email владельца: войдите в `admin.html` правильным паролем, нажмите «Подтвердить email», перейдите по письму, затем выйдите и войдите заново. До этого записи запрещены серверными правилами. Кнопка не создаёт аккаунт автоматически.
5. Authentication → Settings → Authorized domains → добавьте домен сайта и `localhost` для локальной проверки. Не отключайте защиту ради входа.
6. Создайте Firestore Database, если её ещё нет. Если в ней уже есть данные — сделайте резервную копию. **Сначала сравните текущие rules с `firestore.rules`: приведённые правила запрещают все остальные коллекции и могут повлиять на другие приложения в этом же Firebase-проекте.** При общем проекте объедините правила осознанно.
7. Разверните проверенные правила. Единственный публичный документ — `site_config/main`; записи — только подтверждённому администратору. Заявки читает владелец заявки или администратор.
8. Откройте админку, сохраните нужные туры/тексты. При пустой базе показаны исходные данные. После первой публикации появляется документ `site_config/main`.
9. Проверьте запуск на телефоне/в другом браузере: сохраните цену/заголовок, убедитесь, что сайт изменился без обновления страницы; отправьте тестовую заявку, поменяйте статус, проверьте кабинет. Удалите тестовые заявки из Firebase Console.

### Публикация на Firebase Hosting

В каталоге проекта, на машине владельца:

```bash
npm install -g firebase-tools
firebase login
firebase use kubanadventures
# ВАЖНО: сначала согласуйте rules с текущим проектом и сделайте backup.
firebase deploy --only firestore:rules,hosting
```

Для своего домена добавьте его в Hosting и Authorized domains. Файлы можно разместить на другом статическом HTTPS-хостинге, но Firestore rules всё равно развёртываются отдельно. Для работы Auth/Firestore требуется доступ к интернету. Прямая загрузка файла `file://` не является полноценным способом запуска.

## Локальный запуск

```bash
python3 -m http.server 8765
```

- Обычный режим: `http://localhost:8765/index.html` — настоящий Firebase.
- **Изолированное демо:** `http://localhost:8765/index.html?demo=1` и `http://localhost:8765/admin.html?demo=1`.
- Демо работает только на localhost/127.0.0.1, имеет заметную метку, не подключается к Firebase и сохраняет только тестовые данные в этом браузере. В демо введите любые тестовые email/пароль. Вкладки одного браузера синхронизируются через storage/BroadcastChannel. Разные устройства в демо НЕ синхронизируются.
- После смены режима не воспринимайте демо-заявки как реальные. Ключи демо и production-кэша разные; перенос старых `kab_sim_user` и локальных персональных данных намеренно не делается.

## Изображения и контент

Обложки регионов лежат в `images/`. Свои реальные фотографии можно положить туда и указать путь в форме тура; либо использовать прямую HTTPS-ссылку с разрешением на публикацию. Ссылка должна вести на само изображение, не на страницу фотобанка. При ошибке загрузки отображается горный фон. Загрузки файлов в Firebase Storage в этой версии нет: для неё потребуются отдельные правила Storage и учёт ограничений/оплаты.

**Пять регионов в исходном проекте не имеют туров.** Для них добавлены визуальные обложки и корректный экран без маршрутов; вымышленные цены и услуги не публиковались. Создайте настоящие предложения через админку. Тексты о «10+ лет», сертификации МЧС, 50 маршрутах, контакты и цены сохранены из оригинала и не были независимо подтверждены. Перед запуском проверьте их, а также наличие разрешений на маршруты и безопасность экскурсий.

Футер содержит указание на HTML5 UP, на основе которого сделан исходный Dimension-шаблон (CC BY 3.0). Firebase SDK — Google/Firebase, иконки Font Awesome — их исходные лицензии. AI-обложки следует заменить реальными фотографиями перед обещанием конкретных видов туристам.

## Ограничения и следующие шаги

- Это **заявки**, не приём платежей. Цена/название в заявке — справочная копия, не серверное подтверждение стоимости. Финальная стоимость и доступность согласовываются менеджером. Для оплаты нужен backend, который проверяет цену, расписание и формирует заказ; доверять цене из браузера нельзя.
- Сохранение происходит по кнопке, не на каждом нажатии клавиши. После серверного подтверждения изменения приходят посетителям по snapshot.
- Туровый каталог хранится одним массивом: одновременно два администратора, редактирующие **туры**, могут перезаписать изменения друг друга. Тексты и туры сохраняются отдельными merge-полями. Для нескольких редакторов лучше отдельная коллекция туров, версии документов и конфликт-контроль.
- Firestore ограничивает размер документа примерно 1 MiB; правила дополнительно ограничивают каталог 200 турами. Для большого каталога нужна отдельная коллекция и постраничная загрузка.
- Firestore/Auth — персональные данные. До публичного сбора заявок требуется действующая политика обработки данных, законное основание/согласие, сроки хранения и проверка применимых требований локализации. Юридические тексты в проект не выдумывались.
- Рекомендуется App Check, контроль частоты заявок на backend и мониторинг злоупотреблений. Правила ограничивают доступ, но не являются полноценным антиспамом.
- При нестабильной сети Firebase может ожидать ответа на отправленную запись. Не закрывайте админку до результата и проверяйте статус соединения.

## Тестирование

```bash
npm install
# Нужен Chromium в PATH либо CHROMIUM_PATH=/путь/к/chromium
# И сайт, запущенный командой python3 выше.
npm test
```

Тест создаёт два независимых browser contexts и подменяет Firebase исключительно в тесте. Проверяет серверный приоритет над кэшем, ошибки входа/записи, live-обновление текстов/цен/контактов, заявки/статусы, создание/удаление, XSS-экранирование, фильтры и адаптивность. Реальные Firebase rules, доставку писем и ваш хостинг этот тест НЕ проверяет. Подробности в `TEST-REPORT.md`.
